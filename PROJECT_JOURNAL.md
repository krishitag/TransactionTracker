# Project Journal: What, Why, and How (in plain words)

This is my own notes file. It records every decision, the reason for it, and what each part of the project does, so I can explain it clearly in interviews.

Each entry has:
- **What:** what we did or decided
- **Why:** the reason
- **Interview line:** how I'd say it out loud in one or two sentences

---

## 0. The big picture

**What the project is:** A backend that receives card transactions, gives each one a **risk score** (how likely it is to be fraud), explains **why** in plain English ("amount is unusually high", "3 transactions in the last hour"), and lets you **ask questions** about past transactions in normal language ("which merchants had the most high-risk transactions this week?").

**The flow, end to end (once it's finished):**
1. A transaction arrives at `POST /transactions` (FastAPI).
2. We save it in **Postgres**.
3. We look up that card's recent history and compute 4 **features** (numbers that describe the transaction).
4. A trained **Logistic Regression** model turns those features into a fraud probability.
5. We save the score and the top reasons in a `risk_scores` table.
6. We also turn the transaction into a short text summary, convert it to an **embedding** (a list of 384 numbers that captures its meaning), and store it in Postgres using the **pgvector** extension.
7. `POST /ask` finds the most relevant transactions by meaning, adds some hard numbers from Postgres, and asks **Claude** to answer using only that data.
8. A **Next.js dashboard** shows all of this.

**Interview line:** "It's a transaction risk-scoring service. FastAPI takes transactions in, an interpretable logistic regression model scores them and explains each score, and there's a RAG layer on top so analysts can ask questions about the data in plain English."

## 1. Dataset: Sparkov credit card transactions (Kaggle)

**What:** We use `fraudTrain.csv` from Kaggle (`kartik2112/fraud-detection`): about 1.3 million transactions, each with card number, merchant, category, amount, timestamp, and the customer's and merchant's latitude/longitude. Each one is labelled `is_fraud` = 0 or 1.

**Why:** It has the same shape as real transaction data (cards, merchants, times, locations), so the features we build actually mean something. Real bank data isn't public.

**Honest limitation:** The data is **simulated** (generated by a tool called Sparkov). It isn't real fraud. I'll say this plainly in the README.

**Why it's not in git:** The file is hundreds of MB. Git is for code, not big data files, so `data/*.csv` is in `.gitignore`.

**Interview line:** "I used the Sparkov dataset. It's simulated, but it has the same structure as real card data, which let me engineer realistic features like transaction velocity and merchant distance."

---

## 2. The data is very imbalanced (important!)

**What:** Out of 1,296,675 transactions, only 7,506 are fraud. That's about **0.58%**.

**Why it matters:** A "model" that always says "not fraud" would be right 99.4% of the time and would catch zero fraud. So **accuracy is a useless number here.**

**What we do about it:**
- `class_weight="balanced"` tells the model that missing a fraud case costs more than a false alarm, so it actually learns to spot fraud.
- We judge the model with:
  - **Precision:** of the transactions we flagged, how many really were fraud? (Low precision means lots of false alarms.)
  - **Recall:** of all the real fraud, how much did we catch? (Low recall means fraud slips through.)
  - **Confusion matrix:** a 2×2 table of correct and wrong guesses on each side.

**Interview line:** "Fraud was only 0.58% of the data, so accuracy would be misleading. A model that always says 'not fraud' gets 99.4%. I used balanced class weights and evaluated on precision, recall and the confusion matrix instead."

---

## 3. Features: the 4 signals the model looks at

A **feature** is a number that describes a transaction in a way that helps tell fraud from normal spending.

| Feature | Plain meaning | Why it might signal fraud |
|---|---|---|
| `amt` | Transaction amount | Fraudsters often go for big purchases |
| `txns_last_hour` | How many other transactions this card made in the past hour | A stolen card often gets used many times quickly ("velocity") |
| `new_merchant` | Is this the first time this card has paid this merchant? | Unfamiliar merchants are riskier than regular ones |
| `merchant_distance_flag` | Is the merchant unusually far from the customer's home? (true/false) | Card used far from where the person lives |

**How distance works:** We have latitude/longitude for both customer and merchant. The **haversine formula** gives the real distance in km on a round Earth. We then flag anything farther than the **90th percentile** (the distance that 90% of transactions fall under).

**Why distance instead of "country mismatch":** The original idea was "is the merchant in a different country?" This dataset has coordinates, not countries, so distance stands in for it.

**Interview line:** "I engineered velocity, first-time-merchant, and geographic distance features, using the haversine formula on customer and merchant coordinates."

---

## 4. Avoiding data leakage (a good instinct, keep it)

**What:** In `train_model.py`, the 90th-percentile distance threshold is calculated from the **training data only**, and then that same number is applied to the test data.

**Why:** The test set is meant to act like "future data the model has never seen". If we used the test data to pick the threshold, information from the "future" would leak into training, and our test scores would look better than they really are. This is called **data leakage**.

**Also:** `train_test_split(..., stratify=y)` makes sure both the train and test sets keep the same ~0.58% fraud rate. Without it, a random split could put very few fraud cases in the test set.

**Interview line:** "I computed the distance threshold on the training split only, to avoid leakage, and stratified the split so both sets kept the same fraud ratio."

## 5. Model choice: Logistic Regression (not a fancy model)

**What:** scikit-learn's `LogisticRegression`.

**How it works (simply):** It gives each feature a **weight** (a coefficient). For a transaction, it multiplies each feature by its weight, adds them up, and squashes the total into a probability between 0 and 1.

**Why this model:**
- **Explainability for free:** `weight × feature value` shows exactly how much each feature pushed the score up or down. We sort those and turn the biggest ones into reasons like "Amount was much higher than usual". Fancier models (random forests, XGBoost) need extra tools like SHAP to explain themselves.
- In finance, being able to explain *why* a transaction was flagged matters as much as the flag itself.
- It's fast, simple, and easy to defend in an interview.

**Trade-off I'm accepting:** A tree-based model would probably catch more fraud. I chose interpretability over raw performance on purpose, and this is a scoped project, not a production fraud system.

**Interview line:** "I picked logistic regression because each coefficient times feature value gives a per-feature contribution, so every score comes with its reasons built in. I traded some accuracy for explainability, which matters in payments."

## 6. Storage: one database (Postgres + pgvector)

> Originally the plan was two databases (Postgres + MongoDB Atlas). We switched to one; see section 16 for why.

**Postgres (SQL):** stores the transactions and risk scores. It's good for exact, structured questions ("count high-risk transactions per merchant"). Runs locally in Docker during development.

**pgvector (a Postgres extension):** adds a `vector` column type, so embeddings of transaction summaries live in the same database. It's good for "find transactions *similar in meaning* to this question", and it can be combined with normal SQL filters in one query.

**Embeddings:** made locally with `sentence-transformers` (`all-MiniLM-L6-v2`), which turns text into 384 numbers. It's free and runs on my machine, so there are no API costs.

**Interview line:** "Postgres is the single source of truth. With pgvector, the embeddings live next to the data they describe, so I get semantic search and SQL in one place with no sync problem."

## 7. RAG: answering questions about the data

**RAG = Retrieval-Augmented Generation.** Instead of letting the AI guess, we first **retrieve** relevant real data, then ask the AI to **generate** an answer using only that data.

**Our choices:**
- Retrieve **8-10** similar transactions, not 5, so there's more context for good answers.
- For comparison questions ("which category is riskiest?"), also pull a small **aggregate** from Postgres (real counts and averages), because similarity search alone can't do maths over the whole table.
- The prompt tells Claude to **cite transaction IDs and never invent numbers** (we call this "grounding").

**Interview line:** "The /ask endpoint does pgvector similarity search for the top 8-10 transactions, adds a SQL aggregate for comparison questions, and uses a grounding-only prompt so the LLM cites transaction IDs instead of making up numbers."

## 10. Task A1: one shared feature module

**What:** `features.py` used to be a script that printed things. Now it's a small library that other files import:
- `compute_features(df)` adds `txns_last_hour`, `new_merchant` and `distance_km`.
- `distance_threshold(df)` finds the 90th-percentile distance. Only ever call it on **training** data.
- `add_distance_flag(df, threshold)` turns distance into true/false using that saved threshold.
- `FEATURE_COLUMNS` is the single list of the 4 columns the model uses, so training and scoring can't pick different ones.
- The old exploration prints still run if you do `python features.py`, because they're under `if __name__ == "__main__":`. They don't run when another file imports it.

**Why the threshold is a separate step:** The threshold must be learned from training data and then **reused** on test data and live transactions. If `compute_features` worked it out by itself, live scoring would calculate a new threshold from whatever small batch it was given, which would be wrong.

**How live scoring will reuse it (task A3):** Take that card's recent transactions from Postgres, add the new transaction, run `compute_features`, and keep the new transaction's row. Same code, same answers.

**Small robustness fixes I made along the way:**
- The function sorts by card and time itself, so the caller doesn't have to remember to.
- The hourly count now counts the `amt` column (numbers) instead of `trans_num` (text). Newer pandas versions can refuse to do rolling counts on text columns.
- The rolling result is assigned by position after sorting. The old version matched rows by timestamp, which can go wrong when two cards have transactions at the same second.

**How I checked it:** The real CSV wasn't on disk, so I built 6 fake transactions where I knew the correct answers (rows out of order, two cards, a 70-minute gap, a merchant 1° of latitude away ≈ 111 km) and checked every feature value.

**Interview line:** "I pulled feature engineering into one module that both the training pipeline and the live scoring path import, so there's no training/serving skew. Values learned from data, like the distance threshold, are fitted on the training set and passed in, never recomputed at serving time."

## 11. Task A2: training the model and reading the results

**What the code does:**
1. **Scales the features** (`StandardScaler`). `amt` goes up to about $28,000, while the other features are 0/1 or small counts. Scaling changes each one into "how far from a typical transaction is this?" That helps the model train, and it makes the weights comparable with each other.
2. **Fits `LogisticRegression(class_weight="balanced")`** on 1,037,340 training rows (6,005 fraud).
3. **Tests on 259,335 rows it has never seen** (1,501 fraud).
4. **Saves one bundle** to `backend/models/risk_model.joblib` with the model, the distance threshold (112.8 km) and the feature list. Scoring needs all three, so they're saved together and can't get out of sync.

**The results:**

Confusion matrix (test set, cutoff 0.5):

|  | Predicted not fraud | Predicted fraud |
|---|---|---|
| **Actually not fraud** | 241,546 ✅ | 16,288 (false alarms) |
| **Actually fraud** | 317 (missed) | 1,184 ✅ caught |

- **Recall 0.79:** we catch 79% of fraud.
- **Precision 0.068:** only about 1 in 15 flagged transactions is really fraud, so there are lots of false alarms.
- **Accuracy 0.936:** ignore this. A model that always says "not fraud" would score 0.994, which is *higher*, and it would catch nothing.
- **PR-AUC 0.21 vs 0.0058 for random guessing:** the model ranks fraud above normal transactions about **36× better than chance**.

**What the weights tell us (after scaling):**

| Feature | Weight | Meaning |
|---|---|---|
| `amt` | +1.24 | Strongest signal. Fraud averages $531, normal spending $68. |
| `txns_last_hour` | +0.43 | Rapid repeated use raises risk |
| `new_merchant` | +0.30 | First-time merchants raise risk |
| `merchant_distance_flag` | −0.01 | **About zero. This feature does nothing.** |

**An honest finding: the distance feature doesn't work on this data.** The fraud rate is 0.579% for "far" merchants and 0.575% for "near" ones, so they're practically the same. In the Sparkov simulator, merchant locations are random points near the customer whether or not the transaction is fraud. The idea is sound for real data, but this dataset doesn't contain that signal. I'm keeping the feature for now. With a weight of about zero it never shows up as a reason, so it does no harm.

**Precision vs recall at different cutoffs (this decides the risk levels in A3):**

| Flag if probability ≥ | Flagged | Precision | Recall |
|---|---|---|---|
| 0.5 | 17,472 | 0.07 | 0.79 |
| 0.7 | 7,127 | 0.14 | 0.67 |
| 0.9 | 3,476 | 0.23 | 0.53 |
| 0.99 | 1,528 | 0.41 | 0.42 |

Raising the cutoff means fewer false alarms but more fraud getting through. That's the core **precision/recall trade-off**. A bank chooses the cutoff based on what a missed fraud costs compared with an annoyed customer. **Plan for A3:** High risk = ≥ 0.9, Medium = 0.5 to 0.9, Low = below 0.5.

**Known limitations (I should say these before an interviewer does):**
- Only 4 features, so precision is low. Features likely to help a lot later: hour of day (Sparkov fraud clusters late at night), merchant category, and amount compared with *this card's* usual spending.
- The split is random rather than by time. A more realistic test is to train on earlier months and test on later ones. `fraudTest.csv` covers a later period and could be used as that held-out set.
- `new_merchant` treats the first appearance in the dataset as "new", so every card's earliest transactions look new.

**Interview line:** "With 0.58% fraud, accuracy was meaningless, so I evaluated with precision, recall and PR-AUC. The model catches 79% of fraud at a 0.5 cutoff with a PR-AUC about 36× above baseline. I mapped the precision/recall trade-off across cutoffs to set the risk bands. Looking at the coefficients also showed that my distance feature carried no signal in this simulated data. That's the kind of thing an interpretable model makes easy to catch."

## 12. Task A3: scoring one transaction, with reasons

**What `scoring.py` does:** `score_transaction(txn, history)` takes one new transaction plus that card's earlier transactions and returns:

```json
{
  "risk_score": 0.9898,
  "risk_level": "high",
  "reasons": [
    "4 other transactions on this card in the past hour",
    "Amount $300.00 is about 4x the typical transaction ($70)",
    "First time this card has paid Shop B"
  ],
  "features": {...},
  "contributions": {"amt": 1.79, "txns_last_hour": 3.53, "new_merchant": 0.39, "merchant_distance_flag": 0.0}
}
```

**Step by step:**
1. **Why it needs history:** "How many transactions in the last hour?" can't be answered from one transaction. So we put history and the new transaction together, run the **same** `compute_features` used in training, and keep only the new transaction's row (it's marked with a hidden `_is_new` column).
2. **Score:** apply the saved distance threshold, then `predict_proba`.
3. **Risk level:** High ≥ 0.9, Medium ≥ 0.5, otherwise Low (from the table in section 11).
4. **Reasons:** for each feature, `weight × scaled value` = how much it pushed the score up or down compared with an average transaction. We sort them, keep up to 3 that pushed the score up by at least 0.1, and turn each into a sentence. If none qualify, the reason is "No unusual signals".

**Small details that matter:**
- The model file is loaded **once** and reused, not reloaded for every request.
- Every merchant in Sparkov is named `fraud_Something`. That's just how the simulator names them, not a fraud signal, so we strip it from the reason text. Otherwise every reason would *look* like fraud.
- If a history row has exactly the same timestamp as the new transaction, it counts as earlier.

**How I tested it** (on `fraudTest.csv`, a later period the model never saw):

| Case | Score | Level | Top reason |
|---|---|---|---|
| Real fraud, $996 | 0.998 | high | Amount 14× typical |
| Normal $53 purchase | 0.26 | low | First time at this merchant |
| 5th transaction within an hour, $300 | 0.99 | high | 4 other transactions in the past hour |
| Repeat $25 at a known shop | < 0.5 | low | No unusual signals |

**An important honest caveat: the "risk score" isn't a true probability.** Because we trained with `class_weight="balanced"`, the model acts as if fraud were 50% of transactions instead of 0.58%. So 0.99 means "very high risk compared with other transactions", not "a 99% chance this is fraud". That's why the UI and API call it a **risk score**, not a "fraud probability". (Getting a true probability would need an extra step called *calibration*. That's a possible improvement, not needed for this project.)

**Interview line:** "The scorer reuses the exact training feature code on the card's recent history plus the new transaction, so there's no skew. For explanations, I multiply each coefficient by the scaled feature value, which gives each feature's contribution relative to an average transaction, and I turn the top positive contributions into plain-English reasons. Because I used balanced class weights, I present the output as a relative risk score rather than a calibrated probability."

## 13. Task B4: the database tables

**What:** `backend/schema.sql` creates two tables, and `docker-compose.yml` runs Postgres 16 in Docker, creating those tables automatically on the first start. Anyone who clones the repo runs `docker compose up -d` and has a working database.

**Why two tables instead of one:**
- `transactions` holds **facts**: card, merchant, amount, time, locations. They never change.
- `risk_scores` holds the model's **opinion** about each transaction: score, level, reasons. If we retrain the model, opinions can change but facts can't. Keeping them apart also lets us record `model_version`, so we always know which model said what.
- They're linked by `risk_scores.transaction_id → transactions.id` (a **foreign key**).

**Rules built into the database (constraints):**

| Rule | What it stops |
|---|---|
| `trans_num UNIQUE` | Saving the same transaction twice |
| `amount >= 0` | Negative amounts |
| `risk_score BETWEEN 0 AND 1` | Impossible scores |
| `risk_level IN ('low','medium','high')` | Typos like "Hgih" |
| `transaction_id UNIQUE` + foreign key | Two scores for one transaction, or a score for a transaction that doesn't exist |
| `ON DELETE CASCADE` | Leftover scores after a transaction is deleted |

Putting rules in the database (and not only in Python) means that even buggy code can't save bad data. I tested each one, and Postgres rejected them all.

**The index on `(cc_num, trans_time)`:** for every new transaction, scoring asks "show me this card's recent transactions". Without an index, Postgres would read every row in the table. With one, it jumps straight to that card's rows, like a book's index. I checked with `EXPLAIN`, which shows the query plan Postgres uses, and it says `Index Scan using idx_transactions_card_time`.

**Small type choices worth knowing:**
- `cc_num` is `TEXT`, not a number. Card numbers are identifiers, not quantities. You never do maths on them, and storing them as numbers can drop leading zeros.
- `amount` is `NUMERIC(12,2)`, an exact decimal. Floats can't store money exactly (0.1 + 0.2 ≠ 0.3 in floating point).
- `reasons`, `contributions` and `features` are `JSONB`. They're lists and dictionaries that the frontend shows as they are, and JSONB can still be queried.

**What changed along the way:**
- The old `.env` pointed at a Supabase database that no longer exists (free projects get paused or deleted after inactivity). We switched to local Docker Postgres, which was the original plan anyway.
- Docker runs on port **5433**, because a Homebrew Postgres was already using the default 5432.
- The first attempt failed with an I/O error because the Mac's disk was full (188 MB free). Clearing caches freed about 5.7 GB.
- The password in `docker-compose.yml` is a **local development password only**. Real secrets live in `.env`, which is gitignored.

**Interview line:** "I split immutable transaction facts from model-generated risk scores, so rescoring with a new model version doesn't touch source data. Data integrity is enforced in the database with check constraints, a unique transaction ID and foreign keys, and I added a composite index on card and timestamp because every scoring request looks up that card's recent history. I verified that with EXPLAIN."

## 15. Task B6: scoring wired into `POST /transactions`

**The request flow:**

```
client ──POST /transactions──▶ FastAPI
   1. Pydantic validates input            (bad data → 422)
   2. clean: strip "fraud_", times → UTC
   ┌──────────── one DB transaction ────────────┐
   3. INSERT transaction (ON CONFLICT → 409)     │
   4. SELECT minimal card history                │
   5. score_transaction(new, history)            │
   6. INSERT risk_scores (+ model_version)       │
   └──── commit, or roll back everything ───────┘
   7. close connection (always)
◀── 201 {id, risk_score, risk_level, reasons}
```

**Key decisions:**

1. **Validation at the edge.** `amount >= 0`, latitude −90 to 90, longitude −180 to 180. Bad input gets a clear `422` before it reaches the database.
2. **Duplicates → `409 Conflict`.** `INSERT ... ON CONFLICT (trans_num) DO NOTHING RETURNING id` returns nothing if the ID already exists, so we answer "already exists" instead of crashing with a 500. This matters because payment systems often **retry** requests, so receiving the same transaction twice is normal. Handling a repeat safely like this is called **idempotency**.
3. **Atomic: all or nothing.** The insert, scoring and score insert happen inside one database transaction (`with conn:`). If anything fails, Postgres undoes it all, so you never get a transaction without a score. This is the "A" (Atomicity) in **ACID**.
4. **Only the history the features need.** The two features look backwards: velocity needs the **last hour**, and "first time at this merchant" needs to know whether **one** earlier visit exists. So the query fetches just those rows (`UNION` of two small queries), not years of history. Both use the `(cc_num, trans_time)` index, so it stays fast however busy the card is. I checked this on 300 real transactions: **0 differences** from scoring with full history.
5. **Out-of-order arrivals are handled.** History is filtered by the transaction's own `trans_time`, not by when it reached us. A late-arriving old transaction is scored as of its own time.
6. **Column name mapping.** The API and database say `amount` and `trans_time`, while the model was trained on Sparkov's `amt` and `trans_date_trans_time`. `to_scoring_row()` translates in one place.
7. **Model version.** A 12-character fingerprint (SHA-256 hash) of the model file is stored with every score. If you retrain, new scores carry the new version, so you can always tell which model produced which score.
8. **Connection always closed** (`try/finally`), even on errors. The old code leaked a connection on every failed insert, and enough of those would exhaust Postgres's connection limit.

**End-to-end test results** (one card, 4 purchases within 30 minutes):

| Txn | What happened | Score | Level | Reasons |
|---|---|---|---|---|
| t1 | $45 groceries, first visit | 0.25 | low | First time at Kuhic LLC |
| t2 | $30, same shop, 10 min later | 0.29 | low | 1 other transaction in the past hour |
| t3 | $60 gas, new shop | 0.70 | medium | 2 in the past hour; first time at Predovic Inc |
| t4 | $900 electronics, new shop | 0.9998 | high | Amount 13× typical; 3 in the past hour; first time |
| t4 again | duplicate | n/a | **409** | already exists |
| t5 | amount −5 | n/a | **422** | amount must be ≥ 0 |

The database held exactly 4 scored rows: the failed requests saved nothing, and merchant names had no `fraud_` prefix.

**Things I learned from the results:**
- **My prediction was wrong, and the model explains why.** I expected t2 (a repeat shop) to score lowest, but t2 (0.29) is slightly above t1 (0.25). The velocity weight (+0.43) is bigger than the new-merchant weight (+0.30), so "1 transaction in the last hour" adds more risk than "first time at this shop" does. With an interpretable model you can check a surprise like this directly against the weights.
- **Velocity is strong enough to push a $60 gas purchase to "medium"** (3 purchases in 20 minutes). That's reasonable for fraud detection, but a real system would tune it, for example by velocity *relative to this card's usual pace*. Good "what would you improve?" material.
- **The IDs started at 4, not 1.** Earlier test inserts used up IDs 1 to 3. Postgres sequences **never roll back**: a rolled-back insert or an `ON CONFLICT` still consumes the number. That's by design, so concurrent inserts never have to wait on each other. Gaps in IDs are normal, and you should never rely on IDs being consecutive.

**Known simplifications (fine for this project, good to mention):**
- A new database connection per request. A production service would use a **connection pool**.
- Scoring runs inside the request. At large scale you might score asynchronously from a queue.

**Interview line:** "The ingest endpoint is idempotent on transaction ID and atomic: the insert, feature lookup, scoring and score write all happen in one database transaction, so there's never an unscored transaction. For features, I query only the history the model needs, the last hour plus one prior visit to the same merchant, using a composite index, and I verified it produces identical scores to the full history."

## 16. Decision change: MongoDB Atlas → pgvector

**What:** the original plan stored embeddings in MongoDB Atlas. Before building it, we switched to **pgvector**, a Postgres extension that adds a `vector` column type and similarity search.

**Why we switched:**

| | MongoDB Atlas | pgvector |
|---|---|---|
| Extra service | Yes (account, IP allowlist, second connection string) | No. It's the Postgres we already run |
| Consistency | Two databases can disagree if one write fails, so you need a backfill/sync job | Transaction + score + embedding saved in **one** DB transaction, all or nothing |
| Filtered search | Vector search in Mongo, filters/joins in Postgres | One SQL query: `WHERE risk_level = 'high' ORDER BY embedding <=> :q LIMIT 10` |
| Deployment | Atlas + Render | Render Postgres supports pgvector |
| Scale limit | Built for very large vector sets | Comfortably millions of rows; we have thousands |

The original reason for Atlas was "one less service than Pinecone". pgvector is **one less service than Atlas**.

**Why this suits a payments company:** transaction data is relational (it needs constraints, foreign keys and ACID). Adding vector search to the existing relational store, instead of adding a new database, is a common industry pattern. It's supported on AWS RDS/Aurora, Google Cloud SQL, Supabase and Neon.

**When I'd pick a separate vector database:** hundreds of millions of vectors, a search workload that needs to scale separately from the transactional DB, or a team that already runs one.

**How the vector index works (HNSW):** comparing a question with every row would be slow at scale. **HNSW** (Hierarchical Navigable Small World) builds a graph where each vector links to its near neighbours, so a search hops through the graph toward the closest matches instead of checking everything. It's *approximate*, very occasionally missing a true top match, in exchange for being much faster. We use **cosine distance** (`vector_cosine_ops`), which compares the *direction* of embeddings, i.e. their meaning, rather than their length.

**A gotcha from switching images: collation mismatch.** After moving the existing database from the `postgres:16` image to `pgvector/pgvector:pg16`, Postgres warned *"collation version mismatch (2.41 vs 2.36)"*.
- A **collation** is the set of rules for sorting text (does "apple" come before "Banana"?). Postgres gets them from the OS library (glibc) inside the container.
- The two images are built on different Linux versions, so their sorting rules can differ.
- Text indexes (like the `trans_num` uniqueness check) store values **in sorted order**. If the rules change underneath them, lookups can miss rows.
- **What we did:** the DB only had 4 test rows, so we recreated it (`docker compose down -v`, then `up -d`). That also proved a fresh install from `schema.sql` works with pgvector.
- **What you'd do in production, keeping the data:** `REINDEX DATABASE risk;` then `ALTER DATABASE risk REFRESH COLLATION VERSION;`. Better still, pin exact image versions so the OS underneath never changes unexpectedly.

**Interview line:** "I originally planned MongoDB Atlas for vector search, then switched to pgvector. Keeping embeddings in the same Postgres as the transactions made writes atomic, removed a sync problem and a service, and let me combine similarity search with SQL filters in a single query. At our scale pgvector is plenty. I'd revisit a dedicated vector store at hundreds of millions of vectors."

## 17. Task C7: summaries and embeddings

**What happens now on every `POST /transactions`** (inside the same all-or-nothing DB transaction as before):
1. Score the transaction (unchanged).
2. **Write a one-sentence summary**, the way a person would describe it:
   > "HIGH risk (score 1.00): $899.99 online shopping purchase at Shiny Electronics on Sunday 21 Jun 2020 at 12:30 (afternoon), card ending 3333. Reasons: Amount $899.99 is about 13x the typical transaction ($70); 3 other transactions on this card in the past hour."
3. **Embed it**: `all-MiniLM-L6-v2` turns the sentence into 384 numbers.
4. **Save** the summary and embedding in `risk_scores` with the score.

**Choices and why:**
- **Readable categories.** `shopping_net` becomes "online shopping". The embedding model understands English, not dataset codes, so a question about "online shopping" should land near these summaries.
- **Day and time of day in the text** ("Sunday … afternoon", "late night"), so time-flavoured questions have something to match.
- **Only the last 4 card digits** in the text, like a receipt. Full card numbers don't belong in free text.
- **Normalised vectors** (length exactly 1). Cosine distance then compares only *direction*, i.e. meaning, and the maths gets simpler.
- **No extra library to store vectors.** pgvector accepts text like `'[0.12,-0.03,…]'` with `::vector`, so a tiny `to_pgvector()` helper is enough.
- **The model loads once, at startup.** Loading takes seconds and encoding takes milliseconds, so loading per request would be wasteful.
- **One `build_summary()`** is used by both the API and the backfill script, so summaries are always written the same way. Same principle as the shared `features.py`.

**Sanity check (before touching the database):** 4 test summaries, 5 questions.

| Question | Best match | Similarity |
|---|---|---|
| "suspicious online electronics purchase" | the $900 electronics (high) | 0.45 |
| "normal grocery shopping" | the $45 grocery (low) | 0.36 |
| "expensive flight or trip" | the $1,200 travel (high) | **0.52**, though "flight" and "trip" never appear |
| "card used many times in quick succession" | the 2-in-an-hour gas purchase | 0.30 |
| "transactions in the middle of the night" | the 2:15 am gas purchase | 0.21 (barely ahead of a tie) |

**Lesson: embeddings are great at "what is this about" and weak at precise facts** (exact times, counts, amounts, "the most"). That's why `/ask` (C8) combines **vector search** (find relevant examples) with **SQL** (precise filters and counts). Using both is called **hybrid retrieval**.

**Helper scripts:**
- `backfill_embeddings.py` embeds any rows missing an embedding, in batches of 256. `--all` re-embeds everything, e.g. after changing the summary wording. Because Postgres is the source of truth, embeddings can always be rebuilt from it.
- `seed_transactions.py` sends **2,440 real transactions** from `fraudTest.csv` (40 cards, 207 fraud) through the real API in time order, so each card builds history naturally. It's safe to re-run, since duplicates return 409 and are skipped.
  - ⚠️ **The seed is deliberately fraud-heavy (~8.5% vs the real 0.58%)** so the demo has enough fraud to explore. Never quote it as the real fraud rate.

**Results after seeding (2,440 transactions, all returned 201, all embedded):**

| Risk level | Transactions | Actually fraud |
|---|---|---|
| high | 129 | **110** (85%) |
| medium | 324 | 54 |
| low | 1,987 | 43 (missed) |

- Of the 207 frauds, 110 (53%) landed in **high**, the same 53% recall we measured on the test set at the 0.9 cutoff (section 11). The model behaves consistently on new data.
- 164 of 207 (79%) were flagged medium or high. 43 slipped through as low.
- ⚠️ **"85% of high-risk are fraud" is inflated by the fraud-heavy seed.** At the real 0.58% fraud rate, precision at this cutoff was about 23% (section 11). Precision depends on how common fraud is, but recall doesn't. That's a classic trap worth knowing.

**First vector search ("5 most similar to this fraud"):**

| Distance | Summary |
|---|---|
| 0.000 | HIGH: $1,159.89 online shopping at Labadie, Treutel and Bode (the fraud itself) |
| **0.027** | **LOW: $91.11 online shopping at Labadie, Treutel and Bode** |
| 0.238 | HIGH: $874.71 in-store shopping at Baumbach, Hodkiewicz and Walsh |
| 0.251 | HIGH: $880.31 online shopping at Heathcote, Yost and Kertzmann |
| 0.252 | MEDIUM: $246.65 online misc at Parisian, Schiller and Altenwerth |

**The surprise: the closest match is a *low-risk* $91 purchase**, because it's at the same merchant. The long, distinctive merchant name dominates the embedding more than "HIGH" vs "LOW" or $1,160 vs $91. Results 3 to 5 do show the model finding other big, high-risk shopping purchases at different merchants, which is real semantic similarity.

**What this teaches:** embeddings capture *what a text is about* (merchant, category), not *which facts matter most to us* (risk level, amount). So when a question says "high-risk", we must **filter with SQL** (`WHERE risk_level = 'high'`) and then rank by similarity. This is the main practical reason for pgvector: filtering and ranking happen in one query.

**All the useful queries are saved in `backend/queries.sql`**, each with a comment explaining it. Run them all with `psql ... -f backend/queries.sql`. SQL concepts worth knowing from that file:
- `count(*) FILTER (WHERE …)` counts only matching rows, inside a `GROUP BY`.
- `sum(sum(x)) OVER ()` is a **window function**: the grand total next to each group's total, which gives percentages in one query.
- `features ->> 'txns_last_hour'` reads a field out of a JSONB column.
- `jsonb_array_elements_text(reasons)` turns a JSON list into rows, so you can count them.
- `ORDER BY embedding <=> (SELECT …) LIMIT k` is the standard pgvector nearest-neighbour query shape.
- `EXPLAIN ANALYZE` shows how Postgres actually ran a query and whether it used an index.

**Interview line:** "On ingest, each transaction gets a natural-language summary embedded with MiniLM and stored in pgvector in the same transaction as its risk score, so search data can never drift from the source. I verified that semantic matching works, and also saw where it doesn't: precise filters like time or counts. That's why the question-answering layer uses hybrid retrieval, vector search for relevance plus SQL for exact facts."

## 18. Task C8: `POST /ask`, questions in plain English

**Request:** `{"question": "Which categories have the most high-risk transactions?"}`
**Response:** the answer text, the transactions it cites (ID, trans_num, summary), any citations we removed, the filter applied, and which model answered.

**How it works:**

```
question
  │
  ├─ 1. keyword filter: "high-risk" → WHERE risk_level = 'high'   (none if 0 or 2+ levels named)
  ├─ 2. embed question (MiniLM) → pgvector: 10 closest summaries   (EXAMPLES)
  ├─ 3. 4 small SQL aggregates over the whole DB                   (STATISTICS)
  │      by risk level · top categories · top merchants · time of day
  │   ── database connection closed here ──
  ├─ 4. Claude Opus 5.5 with grounding rules + <data>STATISTICS + EXAMPLES</data>
  └─ 5. verify every [#ID] cited was in EXAMPLES; strip any that weren't
```

**Key decisions and why:**

1. **Hybrid retrieval.** EXAMPLES come from vector search (good at "what is this about"), STATISTICS come from SQL (good at exact counts and rankings). Section 17 showed embeddings can't count and get distracted by merchant names, so neither alone is enough.
2. **Always send the statistics.** The original plan was to add them only for comparison questions, but detecting those is itself error-prone. They're about 40 lines, so always including them is cheap and removes a failure mode.
3. **A simple keyword filter for risk level** (not an AI-chosen filter). It's predictable, testable, and visible in the response (`risk_level_filter`). If two levels are named ("compare high and low"), we don't filter. *Possible upgrade:* let Claude choose filters through tool use, or generate SQL itself ("text-to-SQL"). That's more flexible but harder to keep safe.
4. **Grounding rules in the system prompt:** use only the given data; use STATISTICS for counts, because EXAMPLES are only a sample; cite as `[#ID]`; say so when the data can't answer; the risk score isn't a probability.
5. **Citation verification in code.** We don't just *ask* Claude to cite correctly, we **check**. Any `[#ID]` that wasn't in the examples is removed and reported in `removed_invalid_citations`. "Trust, but verify."
6. **Prompt-injection guard.** Merchant names come from outside data, and someone could name a merchant "Ignore previous instructions…". All data goes inside `<data>` tags, and the system prompt says text there is data, never instructions. Also, the `/ask` database session is `READ ONLY`, so even a fully tricked model couldn't change data through this endpoint (and the model never writes SQL anyway).
7. **Close the DB connection before calling Claude.** Claude takes seconds. Holding a connection that long would let a few slow questions use up the pool. So: read, close, then call.
8. **Model: Claude Opus 5.5 at effort `medium`.** Opus 5.5 is the current default model, and thinking is always on for it. Effort controls how much it thinks: `medium` (the model's default, set explicitly) suits a short, grounded Q&A. A question costs roughly 1–2 cents.
9. **Server-side refusal fallback** (`fallbacks="default"`). If the model declines on safety grounds, the API automatically re-runs the request on a suitable fallback model in the same call. If everything declines (`stop_reason == "refusal"`), we return a polite "can't answer" instead of an error.
10. **Clear errors, typed exceptions:** no key → 503 "not configured"; bad key → 503; rate limit → 429; Claude down or unreachable → 502. `/transactions` keeps working without a key. **Bug found while testing:** with no credentials at all, the SDK raises a plain `TypeError` (not its own error type), which would have become a confusing 500. We now check for credentials up front.

**Update: switchable LLM provider, Gemini by default.** To use a free API key, `/ask` now supports **Google Gemini** (free tier from Google AI Studio) as well as Claude, chosen by one setting in `.env`: `LLM_PROVIDER=gemini` (default) or `claude`.
- **Only the "call the model" step changed.** Retrieval, the grounding prompt, `<data>` fencing, citation verification and the read-only DB session are shared, so both providers get the same safety checks.
- **Provider-specific errors become three of our own** (`LLMNotConfigured` → 503, `LLMRateLimited` → 429, `LLMUnavailable` → 502), so `main.py` doesn't need to know which provider is in use. This is the **adapter pattern**: one interface, interchangeable implementations.
- **Each SDK is imported only inside its own function**, so the app runs with just one of them installed.
- Gemini settings: `temperature=0.2` (low randomness, which suits factual answers from data). The model is set by `GEMINI_MODEL` (default `gemini-3.8-flash`, the newest **stable** flash model available to our key), so it can change without touching code. We avoided `*-preview` models (they can change or disappear) and `gemini-flash-latest` (an alias that silently changes over time, which hurts reproducibility).
- **Secret hygiene:** an API key got pasted into a chat, so it was treated as leaked and **rotated** (deleted, new one created, stored only in the gitignored `.env`).
- **Free-tier trade-offs (say these in interviews):** per-minute and per-day request limits (we return a clear 429), and Google may use free-tier prompts to improve its products. That's fine for simulated data, but for real customer data you'd use a paid tier or a provider with a no-training/zero-retention agreement.

**End-to-end test results (Gemini 3.8 Flash, 2,440 seeded transactions):**

| Question | Result |
|---|---|
| "Which spending categories have the most high-risk transactions?" | ✅ Exact counts from STATISTICS (shopping_net 60, shopping_pos 27, …); no citations (correct for a counting question); filter `high` applied |
| "Show me suspicious late-night online shopping purchases" | ✅ Honestly said no example matched; offered close alternatives (22:00–23:48 high-risk), clearly labelled; 5 valid citations |
| "Why were the high-risk transactions flagged?" | ✅ Named the model's 3 signals with 9 valid citations; numbers match the summaries |
| "What was the average transaction amount in Mumbai?" (trap) | ✅ "The data does not contain location information" (no invented number) |

`removed_invalid_citations` was empty every time.

**What the answers revealed:**
1. **Retrieval gap for time questions.** Embeddings don't capture "late night" precisely (as seen in section 17), so no late-night high-risk examples were retrieved. *Fix idea:* keyword filters for time of day and category, like the risk-level filter.
2. **A blind spot in the model itself:** the statistics show **65 confirmed frauds late at night (0–6) but only 14 high-risk transactions** in that window. The model has no time-of-day feature, so it can't see this pattern. *Fix idea:* add an hour/late-night feature and retrain. **Interview story:** "Using the question-answering layer on my own data surfaced a gap in my model, so I knew exactly which feature to add next."
3. Minor: STATISTICS show raw category codes (`shopping_net`); they could use the readable names the summaries already use.

**Interview line (provider):** "The LLM sits behind a small adapter, so I can switch between Gemini and Claude with one config value. Retrieval, grounding and citation checks don't depend on the model provider."

**Interview line:** "The /ask endpoint does hybrid retrieval: a keyword-derived SQL filter plus pgvector similarity for relevant examples, and SQL aggregates for exact numbers, because embeddings can't count. Claude answers under a grounding-only prompt, with the data fenced off against prompt injection, and I verify every cited transaction ID in code, stripping any it wasn't given. The database session is read-only and closed before the model call."

## 19. Model v2: the night-time feature (and smarter /ask filters)

**How we found it:** the `/ask` statistics showed 65 confirmed frauds late at night but only 14 flagged high-risk. The model had no notion of time.

**Step 1: look at the data before adding anything** (training split only, to avoid leakage):

| Hours | Share of transactions | Share of all fraud | Fraud rate |
|---|---|---|---|
| **22:00–03:59** | 23.5% | **84.7%** | **2.09%** |
| all other hours | 76.5% | 15.3% | 0.12% |

The edge is sharp (1.46% at 3 am, 0.11% at 4 am). **Correction:** our earlier "late night = 0–6" bucket was in the wrong place, and 22:00–23:59 alone holds 51% of fraud. All time buckets (summaries, `/ask` stats, `queries.sql`) now use 22:00–04:00 for "late night".

**Step 2: the feature.** `night_time` = the hour is in {22, 23, 0, 1, 2, 3}. It's a yes/no feature, so the explanation stays readable: *"Made at 23:15, in the 22:00-04:00 window when most fraud happens."* It's defined once in `features.py` (`NIGHT_HOURS`), and training, scoring, summaries and `/ask` all import it from there.

**Step 3: compare v1 and v2 on the same test set:**

| | v1 (4 features) | v2 (+night_time) |
|---|---|---|
| PR-AUC | 0.210 | **0.285** (+36%) |
| night_time weight | n/a | **+1.14** (as strong as amount, +1.14) |
| At 0.9: alerts / precision / recall | 3,476 / 22.9% / 53.1% | **2,725 / 32.9% / 59.8%** |
| At 0.9: night-time fraud caught | 52.8% | **61.8%** |
| At 0.9: daytime fraud caught | 54.6% | 48.5% ⚠️ |

**The trade-off (be ready to explain this):** logistic regression *adds up* evidence, so "not at night" now counts *against* a transaction. Daytime frauds start lower, and fewer of them reach the threshold. Daytime is only 15% of fraud, so overall v2 is clearly better, but it's a real cost. *Fixes for later:* "unusual hour *for this card*" (personal baselines), or a tree-based model (e.g. gradient boosting) that can learn combinations like "big amount at 2pm". The cost is less direct explainability (it would need SHAP).

**Step 4: re-tune the risk bands.** With v2, a 0.5 cutoff would flag ~32k test transactions, because every night transaction gets lifted. So **Medium moved from 0.5 to 0.7**:

| | v1 at 0.5 (old medium) | v2 at 0.7 (new medium) |
|---|---|---|
| Alerts | 17,472 | **8,751** (half) |
| Precision | 6.8% | **13.1%** (about double) |
| Recall | 78.9% | 76.6% (about the same) |

Lesson: **when the model changes, re-check the thresholds.** They're tuned to a particular model's score distribution.

**Example (same $300 first-time purchase):** 23:15 scores **0.89 (medium)** with night-time as the top reason; 14:15 scores **0.35 (low)**.

**Model version:** the fingerprint changed automatically from `c8b8b28efe16` to `f683e347ae3d`, so every stored score says which model produced it.

**/ask retrieval improvements (same keyword-filter approach as risk level):**
- **Time of day:** "late night / after midnight / at night / overnight" → hours 22–03 (the same window as the model); morning, afternoon and evening too. If two windows are named ("night and evening"), no filter is applied.
- **Category:** "online shopping" → `shopping_net`; "shopping" → both shopping categories; "groceries", "gas/fuel", "travel/flights/hotels", "food/dining", etc. Specific phrases are matched first and then removed, so "online shopping" doesn't also match plain "shopping". "home" is deliberately excluded, because "far from home" isn't a category.
- **Fallback:** if the filters match nothing, search without them and **tell the model** the examples don't satisfy the filters, so it can't present near-misses as matches.
- **Readable categories in the statistics** ("online shopping", not `shopping_net`).
- The response now includes `filters` (what was detected) and `filters_relaxed`.

**Re-seeded with v2 (same 2,440 transactions), compared with v1:**

| | v1 | v2 |
|---|---|---|
| High: alerts / actually fraud | 129 / 110 (85%) | **141 / 126 (89%)** |
| Fraud caught as high | 110 / 207 (53%) | **126 / 207 (61%)** |
| Total alerts (high + medium) | 453 | **254 (−44%)** |
| Alerts that were real fraud | 36% | **61%** |
| Fraud missed (low) | 43 | 53 ⚠️ |

This matches the test-set analysis: better high-risk detection and far fewer false alarms, at the cost of a few more misses (daytime fraud plus the stricter medium cutoff). Precision here is inflated by the fraud-heavy seed.

**/ask re-test:** "Show me suspicious late-night online shopping purchases" now detects `late night (22:00-04:00)` + `shopping_net` with `filters_relaxed: false`. All 7 citations are online shopping between 22:09 and 23:58, with 0 invalid citations. The statistics show 172 of 207 seeded frauds (83%) happened at night, consistent with the 84.7% in training.

**Habit: verify the LLM's specific claims against the source.** The answer labelled some transactions "not confirmed fraud". The labels were in its prompt but not in the returned summaries, so we checked them with SQL (`SELECT id, is_fraud FROM transactions WHERE id IN (...)`) rather than taking the model's word for it.

**Interview line:** "Asking my own system questions showed that 85% of fraud happens between 10 pm and 4 am, which my model couldn't see. I added a night-time feature: PR-AUC went up 36%, and at the high-risk cutoff alerts dropped 22% while recall rose from 53% to 60%. The cost was weaker recall on daytime fraud, because logistic regression is additive. I documented it, re-tuned the medium threshold for the new score distribution, and would address it next with per-card time baselines or a tree model."

## 20. Task D9a: read endpoints for the dashboard

**What:** three read-only endpoints the dashboard calls, plus CORS.

| Endpoint | Returns |
|---|---|
| `GET /stats` | Tile numbers: total, high/medium/low, total and high-risk amounts, model version |
| `GET /transactions?risk_level=high&limit=25&offset=0` | One page of transactions (newest first) + `total` for page numbers |
| `GET /transactions/{id}` | One transaction (so a clicked `[#660]` citation can be shown even if it's not on the current page); 404 if missing |

**Decisions and why:**
- **Only the last 4 card digits leave the API** (`right(cc_num, 4)`). The browser never needs the full number. This is **data minimisation**: don't expose what the client doesn't need. In a real payments system, full card numbers fall under PCI DSS rules.
- **Validation before SQL:** `risk_level` is typed as `Literal["high","medium","low"]`, so anything else returns 422 automatically. `limit` is capped at 1–100, so nobody can request a million rows at once.
- **Pagination with `LIMIT/OFFSET` + `count(*) OVER ()`.** A **window function** adds the total match count to every row, so one query returns both the page and the total. *Known limitation:* OFFSET gets slower deep into large tables. At scale you'd use **keyset pagination** ("rows older than the last one I saw").
- **Every read runs in a `READ ONLY` transaction** through one helper (`read_rows`), so these endpoints can't change data even by mistake.
- **CORS only for the known frontend origin** (`http://localhost:3100`, configurable with `FRONTEND_ORIGINS`), not `*`. Browsers block a page on one origin from reading another origin's responses unless the server allows it. That's the **same-origin policy**, and CORS is the server saying who's allowed.
  - **Real bug this caught:** another Next.js project was already on port 3000, so the dashboard silently started on 3001. That would have been blocked by CORS, while the *other* app would have been allowed. Fix: pin the dashboard to its own port (`next dev -p 3100`) and allow exactly that origin. Lesson: an origin is scheme + host + **port**, so `localhost:3000` and `localhost:3001` are different origins.

**Tested:** stats 2,440 / 141 / 113 / 2,186; filtered page `total: 141` with `card_last4` only; #660 found; unknown ID → 404; `risk_level=extreme` → 422.

**Interview line:** "The dashboard reads through paginated, read-only endpoints that validate input with types, return only the last four card digits, and allow CORS for the frontend origin only. Pagination uses a window function so one query gives both the page and the total."

## 23. Manual test: the ask panel timeout, and a backup Gemini key

**What happened:** the dashboard, filters, table and reasons all passed my manual test. But asking a question showed *"No answer after 60 seconds"*. Calling `/ask` directly (without the browser) took **89 seconds** and returned **Gemini 504 "Deadline expired"**. A tiny "reply OK" test then got **429 rate limit**. So Google's free-tier model was overloaded and my quota was hit. That part was Google's side, not our code or network.

**The bug in our code: the timeout budgets were in the wrong order.** The browser gave up at 60s, but the backend allowed Gemini 45s × 2 attempts, which is about 90s. The backend's clear error ("rate limit", "overloaded") arrived after the browser had already stopped listening, so I only ever saw a vague timeout.
- **Rule:** timeouts must *shrink* as you go deeper. Browser 60s → backend 50s total → each Gemini call 40s. The inner layer always fails first, so its specific error reaches the user.
- **No automatic retry of a slow call.** Retrying a request that just took 40s to fail doubles the wait and spends more quota, during exactly the moment the service is struggling.

**Backup key (`GEMINI_API_KEY_2`, optional):**
- Used **only on 429 (rate limit)**. A 429 comes back quickly, so there's time to try again. It is **not** used on 503/504/timeouts: those mean Google's model is overloaded for everyone, so another key hits the same servers. In that case the message is "Gemini is overloaded right now; try again in a minute."
- **Quota is per Google project, not per key.** A second key in the same project shares the limit and would be useless. It has to come from a different project.
- A rate-limited key is **moved to the back for 60 seconds** (a simple *cooldown*), so the next question goes straight to the working key instead of wasting a call.
- The backup is only started if **at least 15s of the 50s budget** is left.
- Logs say "key 1" / "key 2", never the key itself.
- With no second key, the behaviour is the same as before (minus the retry).
- Later generalised to up to 5 keys (`GEMINI_API_KEY_2` … `_5`), tried in order on 429 only; the same 50s budget still caps the total time.

**Tested:** 10 offline tests with fake Gemini responses (no real API calls): key 1 works; 429 → key 2; both limited; 504 and timeout don't switch keys; a bad key 2 is named correctly; no keys; the cooldown skips key 1 on the next question; no backup when the budget is nearly used up.

**Then: thinking level LOW, and logging every failure.** Two more questions failed with 502 and no rate-limit lines, so the model was too slow, not over quota. `gemini-3.8-flash` "thinks" (reasons internally) before answering, by default at length. Our questions are summaries of data we already retrieved, so deep reasoning adds time, not accuracy, and when Google is busy that time crosses our 40s limit. We now set `thinking_level=low` (configurable with `GEMINI_THINKING`). We also log every call's outcome with the error code and seconds taken (`Gemini key 1 failed: 504 after 40.1s`), because we'd been guessing which failure it was. *Lesson: when debugging a dependency, log what it returned and how long it took, so you measure instead of guessing.*

**Answers checked against SQL during the test:**
- *Late-night online shopping:* every statistic and all 8 cited transactions correct.
- *Mumbai (trap):* correctly declined, because we store coordinates, not city names.
- *Large travel purchases at night:* correct but hedged ("can't rule it out"). SQL shows all 14 late-night travel transactions are $1.11–$9.12. The model only saw 10 of them and had no amount statistics for that group, so being cautious was right. The fix is better statistics (backlog 6), not a different prompt.

**Model blind spot found by asking questions: small-amount fraud.** 4 of the 5 largest late-night travel transactions were confirmed fraud, and most were scored Low. Across the whole seed:

| Fraud amount | Fraud | Scored Low | Scored High |
|---|---|---|---|
| $100+ | 159 | 13 | 125 |
| $20–99 | 11 | 7 | 1 |
| under $20 | 37 | **33** | 0 |

33 of the 53 missed frauds are under $20. The model's strongest signal is "amount far above normal", so small frauds look harmless. In real payments these are often **card testing**: a tiny charge to check that a stolen card works before a big one. Catching them needs *sequence* features (several small payments in a row, a small payment followed by a large one on the same card), not the amount alone. Logged as backlog 7.

**The rest of the manual test** (error messages, Enter vs Shift+Enter, backend stopped, phone layout at 400px, keyboard and skip link) passed. It found three small UI issues that automated checks missed:
1. **A gap before the comma after each citation** ("#1945 , #1660"). The button's padding, there for the hover pill, pushed the comma away. Fix: a matching negative margin (`-mx-1 px-1`), so the text sits flush and the hover pill stays.
2. **A thick focus ring on the citation card after a mouse click.** We move focus to the card on purpose, so screen readers announce it, but it's a target, not a control. Fix: the global focus rule now skips `tabindex="-1"` elements, which are only ever focused by code. Real controls keep their ring.
3. **An error that pointed to something hidden.** "…or pick an example below" appeared while the examples were hidden. Fix: keep the examples visible next to that error, and say "above", which is where they actually are.

*Lesson: automated checks measure rules (contrast, sizes, focus exists). A human click-through finds things that are technically valid but wrong in context.*

**Limitation:** a backup key only helps with quota, not with Google outages. A real product would use a paid tier, or fall back to a *different provider* (we already have Claude behind `LLM_PROVIDER`).

**Interview line:** "During manual testing the AI answers timed out. I traced it by calling the API directly: the LLM provider was returning 504s and 429s, but my backend's retries outlasted the browser's timeout, so users saw a generic error instead of the real one. I reordered the timeout budgets so each inner layer fails first, removed retries on slow failures, and added a backup key that's used only for rate limits, with a cooldown, because overload errors wouldn't be fixed by switching keys."
