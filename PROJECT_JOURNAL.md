# Project Journal: What, Why, and How (in plain words)

This is my own notes file. It records every decision, the reason for it, and what each part of the project does, so I can explain it clearly in interviews.

Each entry has:
- **What:** what we did or decided
- **Why:** the reason
- **Interview line:** how I'd say it out loud in one or two sentences

---

## 0. The big picture

**What the project is:** A backend that receives card transactions, gives each one a **risk score** (how likely it is to be fraud), explains **why** in plain English ("amount is unusually high", "3 transactions in the last hour"), and lets you **ask questions** about past transactions in normal language ("which merchants had the most high-risk transactions this week?").

**The flow, end to end (once it's finished):**
1. A transaction arrives at `POST /transactions` (FastAPI).
2. We save it in **Postgres**.
3. We look up that card's recent history and compute 4 **features** (numbers that describe the transaction).
4. A trained **Logistic Regression** model turns those features into a fraud probability.
5. We save the score and the top reasons in a `risk_scores` table.
6. We also turn the transaction into a short text summary, convert it to an **embedding** (a list of 384 numbers that captures its meaning), and store it in **MongoDB Atlas**.
7. `POST /ask` finds the most relevant transactions by meaning, adds some hard numbers from Postgres, and asks **Claude** to answer using only that data.
8. A **Next.js dashboard** shows all of this.

**Interview line:** "It's a transaction risk-scoring service. FastAPI takes transactions in, an interpretable logistic regression model scores them and explains each score, and there's a RAG layer on top so analysts can ask questions about the data in plain English."

## 1. Dataset: Sparkov credit card transactions (Kaggle)

**What:** We use `fraudTrain.csv` from Kaggle (`kartik2112/fraud-detection`): about 1.3 million transactions, each with card number, merchant, category, amount, timestamp, and the customer's and merchant's latitude/longitude. Each one is labelled `is_fraud` = 0 or 1.

**Why:** It has the same shape as real transaction data (cards, merchants, times, locations), so the features we build actually mean something. Real bank data isn't public.

**Honest limitation:** The data is **simulated** (generated by a tool called Sparkov). It isn't real fraud. I'll say this plainly in the README.

**Why it's not in git:** The file is hundreds of MB. Git is for code, not big data files, so `data/*.csv` is in `.gitignore`.

**Interview line:** "I used the Sparkov dataset. It's simulated, but it has the same structure as real card data, which let me engineer realistic features like transaction velocity and merchant distance."

---

## 2. The data is very imbalanced (important!)

**What:** Out of 1,296,675 transactions, only 7,506 are fraud. That's about **0.58%**.

**Why it matters:** A "model" that always says "not fraud" would be right 99.4% of the time and would catch zero fraud. So **accuracy is a useless number here.**

**What we do about it:**
- `class_weight="balanced"` tells the model that missing a fraud case costs more than a false alarm, so it actually learns to spot fraud.
- We judge the model with:
  - **Precision:** of the transactions we flagged, how many really were fraud? (Low precision means lots of false alarms.)
  - **Recall:** of all the real fraud, how much did we catch? (Low recall means fraud slips through.)
  - **Confusion matrix:** a 2×2 table of correct and wrong guesses on each side.

**Interview line:** "Fraud was only 0.58% of the data, so accuracy would be misleading. A model that always says 'not fraud' gets 99.4%. I used balanced class weights and evaluated on precision, recall and the confusion matrix instead."

---

## 3. Features: the 4 signals the model looks at

A **feature** is a number that describes a transaction in a way that helps tell fraud from normal spending.

| Feature | Plain meaning | Why it might signal fraud |
|---|---|---|
| `amt` | Transaction amount | Fraudsters often go for big purchases |
| `txns_last_hour` | How many other transactions this card made in the past hour | A stolen card often gets used many times quickly ("velocity") |
| `new_merchant` | Is this the first time this card has paid this merchant? | Unfamiliar merchants are riskier than regular ones |
| `merchant_distance_flag` | Is the merchant unusually far from the customer's home? (true/false) | Card used far from where the person lives |

**How distance works:** We have latitude/longitude for both customer and merchant. The **haversine formula** gives the real distance in km on a round Earth. We then flag anything farther than the **90th percentile** (the distance that 90% of transactions fall under).

**Why distance instead of "country mismatch":** The original idea was "is the merchant in a different country?" This dataset has coordinates, not countries, so distance stands in for it.

**Interview line:** "I engineered velocity, first-time-merchant, and geographic distance features, using the haversine formula on customer and merchant coordinates."

---

## 4. Avoiding data leakage (a good instinct, keep it)

**What:** In `train_model.py`, the 90th-percentile distance threshold is calculated from the **training data only**, and then that same number is applied to the test data.

**Why:** The test set is meant to act like "future data the model has never seen". If we used the test data to pick the threshold, information from the "future" would leak into training, and our test scores would look better than they really are. This is called **data leakage**.

**Also:** `train_test_split(..., stratify=y)` makes sure both the train and test sets keep the same ~0.58% fraud rate. Without it, a random split could put very few fraud cases in the test set.

**Interview line:** "I computed the distance threshold on the training split only, to avoid leakage, and stratified the split so both sets kept the same fraud ratio."

## 5. Model choice: Logistic Regression (not a fancy model)

**What:** scikit-learn's `LogisticRegression`.

**How it works (simply):** It gives each feature a **weight** (a coefficient). For a transaction, it multiplies each feature by its weight, adds them up, and squashes the total into a probability between 0 and 1.

**Why this model:**
- **Explainability for free:** `weight × feature value` shows exactly how much each feature pushed the score up or down. We sort those and turn the biggest ones into reasons like "Amount was much higher than usual". Fancier models (random forests, XGBoost) need extra tools like SHAP to explain themselves.
- In finance, being able to explain *why* a transaction was flagged matters as much as the flag itself.
- It's fast, simple, and easy to defend in an interview.

**Trade-off I'm accepting:** A tree-based model would probably catch more fraud. I chose interpretability over raw performance on purpose, and this is a scoped project, not a production fraud system.

**Interview line:** "I picked logistic regression because each coefficient times feature value gives a per-feature contribution, so every score comes with its reasons built in. I traded some accuracy for explainability, which matters in payments."

## 6. Storage: why two databases?

**Postgres (SQL):** stores the transactions and risk scores. It's good for exact, structured questions ("count high-risk transactions per merchant"). Runs locally in Docker during development.

**MongoDB Atlas Vector Search:** stores embeddings of transaction summaries. It's good for "find transactions *similar in meaning* to this question". We picked it over Pinecone because Atlas does both normal documents and vector search, so it's one less service to manage.

**Embeddings:** made locally with `sentence-transformers` (`all-MiniLM-L6-v2`), which turns text into 384 numbers. It's free and runs on my machine, so there are no API costs.

**Interview line:** "Postgres is the source of truth for structured queries, and MongoDB Atlas holds the vector embeddings for semantic search. I picked Atlas over Pinecone to keep the number of services down."

---

## 7. RAG: answering questions about the data

**RAG = Retrieval-Augmented Generation.** Instead of letting the AI guess, we first **retrieve** relevant real data, then ask the AI to **generate** an answer using only that data.

**Our choices:**
- Retrieve **8-10** similar transactions, not 5, so there's more context for good answers.
- For comparison questions ("which category is riskiest?"), also pull a small **aggregate** from Postgres (real counts and averages), because similarity search alone can't do maths over the whole table.
- The prompt tells Claude to **cite transaction IDs and never invent numbers** (we call this "grounding").

**Interview line:** "The /ask endpoint does vector search for the top 8-10 transactions, adds a SQL aggregate for comparison questions, and uses a grounding-only prompt so the LLM cites transaction IDs instead of making up numbers."

## 10. Task A1: one shared feature module

**What:** `features.py` used to be a script that printed things. Now it's a small library that other files import:
- `compute_features(df)` adds `txns_last_hour`, `new_merchant` and `distance_km`.
- `distance_threshold(df)` finds the 90th-percentile distance. Only ever call it on **training** data.
- `add_distance_flag(df, threshold)` turns distance into true/false using that saved threshold.
- `FEATURE_COLUMNS` is the single list of the 4 columns the model uses, so training and scoring can't pick different ones.
- The old exploration prints still run if you do `python features.py`, because they're under `if __name__ == "__main__":`. They don't run when another file imports it.

**Why the threshold is a separate step:** The threshold must be learned from training data and then **reused** on test data and live transactions. If `compute_features` worked it out by itself, live scoring would calculate a new threshold from whatever small batch it was given, which would be wrong.

**How live scoring will reuse it (task A3):** Take that card's recent transactions from Postgres, add the new transaction, run `compute_features`, and keep the new transaction's row. Same code, same answers.

**Small robustness fixes I made along the way:**
- The function sorts by card and time itself, so the caller doesn't have to remember to.
- The hourly count now counts the `amt` column (numbers) instead of `trans_num` (text). Newer pandas versions can refuse to do rolling counts on text columns.
- The rolling result is assigned by position after sorting. The old version matched rows by timestamp, which can go wrong when two cards have transactions at the same second.

**How I checked it:** The real CSV wasn't on disk, so I built 6 fake transactions where I knew the correct answers (rows out of order, two cards, a 70-minute gap, a merchant 1° of latitude away ≈ 111 km) and checked every feature value.

**Interview line:** "I pulled feature engineering into one module that both the training pipeline and the live scoring path import, so there's no training/serving skew. Values learned from data, like the distance threshold, are fitted on the training set and passed in, never recomputed at serving time."

## 11. Task A2: training the model and reading the results

**What the code does:**
1. **Scales the features** (`StandardScaler`). `amt` goes up to about $28,000, while the other features are 0/1 or small counts. Scaling changes each one into "how far from a typical transaction is this?" That helps the model train, and it makes the weights comparable with each other.
2. **Fits `LogisticRegression(class_weight="balanced")`** on 1,037,340 training rows (6,005 fraud).
3. **Tests on 259,335 rows it has never seen** (1,501 fraud).
4. **Saves one bundle** to `backend/models/risk_model.joblib` with the model, the distance threshold (112.8 km) and the feature list. Scoring needs all three, so they're saved together and can't get out of sync.

**The results:**

Confusion matrix (test set, cutoff 0.5):

|  | Predicted not fraud | Predicted fraud |
|---|---|---|
| **Actually not fraud** | 241,546 ✅ | 16,288 (false alarms) |
| **Actually fraud** | 317 (missed) | 1,184 ✅ caught |

- **Recall 0.79:** we catch 79% of fraud.
- **Precision 0.068:** only about 1 in 15 flagged transactions is really fraud, so there are lots of false alarms.
- **Accuracy 0.936:** ignore this. A model that always says "not fraud" would score 0.994, which is *higher*, and it would catch nothing.
- **PR-AUC 0.21 vs 0.0058 for random guessing:** the model ranks fraud above normal transactions about **36× better than chance**.

**What the weights tell us (after scaling):**

| Feature | Weight | Meaning |
|---|---|---|
| `amt` | +1.24 | Strongest signal. Fraud averages $531, normal spending $68. |
| `txns_last_hour` | +0.43 | Rapid repeated use raises risk |
| `new_merchant` | +0.30 | First-time merchants raise risk |
| `merchant_distance_flag` | −0.01 | **About zero. This feature does nothing.** |

**An honest finding: the distance feature doesn't work on this data.** The fraud rate is 0.579% for "far" merchants and 0.575% for "near" ones, so they're practically the same. In the Sparkov simulator, merchant locations are random points near the customer whether or not the transaction is fraud. The idea is sound for real data, but this dataset doesn't contain that signal. I'm keeping the feature for now. With a weight of about zero it never shows up as a reason, so it does no harm.

**Precision vs recall at different cutoffs (this decides the risk levels in A3):**

| Flag if probability ≥ | Flagged | Precision | Recall |
|---|---|---|---|
| 0.5 | 17,472 | 0.07 | 0.79 |
| 0.7 | 7,127 | 0.14 | 0.67 |
| 0.9 | 3,476 | 0.23 | 0.53 |
| 0.99 | 1,528 | 0.41 | 0.42 |

Raising the cutoff means fewer false alarms but more fraud getting through. That's the core **precision/recall trade-off**. A bank chooses the cutoff based on what a missed fraud costs compared with an annoyed customer. **Plan for A3:** High risk = ≥ 0.9, Medium = 0.5 to 0.9, Low = below 0.5.

**Known limitations (I should say these before an interviewer does):**
- Only 4 features, so precision is low. Features likely to help a lot later: hour of day (Sparkov fraud clusters late at night), merchant category, and amount compared with *this card's* usual spending.
- The split is random rather than by time. A more realistic test is to train on earlier months and test on later ones. `fraudTest.csv` covers a later period and could be used as that held-out set.
- `new_merchant` treats the first appearance in the dataset as "new", so every card's earliest transactions look new.

**Interview line:** "With 0.58% fraud, accuracy was meaningless, so I evaluated with precision, recall and PR-AUC. The model catches 79% of fraud at a 0.5 cutoff with a PR-AUC about 36× above baseline. I mapped the precision/recall trade-off across cutoffs to set the risk bands. Looking at the coefficients also showed that my distance feature carried no signal in this simulated data. That's the kind of thing an interpretable model makes easy to catch."
